# 승인된 후보 준비·서명 요청 자동화

2026-10-03 도입. 기존 Master Signing 도우미와 배포 ZIP은 변경하지 않는다.

## 실행 흐름

1. 비공개 통합 검증 때 고정 ZIP과 전송 자료를 미리 준비한다. 이 작업은 공개/서명 승인이 아니다.
2. Master가 해당 버전의 배포·서명 요청을 명시 승인한 뒤, 검토된 배포 파일과 후보 명세만 공개 저장소로 이관한다.
3. `publisher/candidates/vX.Y.Z.json` 변경으로 `prepare-candidate.yml`이 실행된다. 실제 Windows에서 불변 ZIP, 공개 다운로드14개, 설치된 도우미 인식7개를 확인한다.
4. 통과하면 보관 요청·활성 계획·current-request를 한 커밋으로 게시한다. 담당자가 검증 결과를 다시 수동 복사해 요청을 만드는 대기를 제거했다.
5. 도우미 승인·서명·전달 후 기존 자동 운영 서명·Windows 적용/복구36개·공개 게시 검사를 수행한다. 대화 완료 보고는 필요 없다.

후보 명세에는 버전·순번·선행 버전, Master ZIP 경로/크기/해시, 공개 내용 검토와 Windows 후보 검증 실행, 변경 안내, 업데이트 경로가 필요하다. `approval`은 `explicit: true`, `scope: master-release`, 승인 시점 및 **동일 버전·순번·ZIP 해시**를 기록한다. 이를 채우는 행위가 사용자 승인을 대신하지 않는다. 승인 전 명세를 활성 경로에 게시하지 않는다.

일반 업데이트 경로는 `online`이다. `legacy-import-once`는 추가 명시 승인과 서명된 원천 목록이 필요하다. 기존 요청이 대기 중이면 다른 후보로 덮어쓰지 않는다. 재실행은 같은 패키지 커밋·요청 payload를 재사용하며, 게시 완료 버전의 서명 요청을 다시 생성하지 않는다. 실패·동시 변경은 강제 덮어쓰기 없이 중단한다.

## 캐시 대기 수정

기존 코드는 동일 raw URL의 오래된 응답을 10초 간격으로 반복 조회하여, 실제 게시됐는데도 121초 뒤 실패했다. 현재는 고정 게시 커밋과 최신 채널 주소를 각각 무인증 조회하고 **정확한 서명 바이트**를 비교한다. 최신 채널 조회에는 게시 해시·시도 번호를 붙여 같은 캐시 응답의 반복 재사용을 방지한다. 최신 채널이 다른 내용을 반환하면 여전히 실패한다. 성공 시 대기하지 않고, 일시 장애에는 최대4회/간격2초/요청 제한10초를 적용한다. 고정 커밋만 확인하고 성공 처리하지 않는다.

- [공통 후보 준비의 실제 Windows 재현](https://github.com/YoubinNa/TRADE-OPERATIONS-SUITE-UPDATES/actions/runs/37085799258): 전체40초, 후보 승인·중복/변조/전송13개, 캐시6개, 실제 공개 다운로드14개와 도우미7개 통과. 기존 v30 요청 바이트 유지 확인. 새 요청·서명·배포는 하지 않았다.
- 일반 기능 검증315개를 서명 준비 때 다시 빌드·실행하지 않는다. 같은 불변 ZIP의 검증 근거를 재사용하되 공개 다운로드·서명 후 적용/복구는 유지한다.
- 후보 사전검사 경과시간과 승인·요청 게시 시각을 PREFLIGHT에 남기고 Actions 단계별 시간을 기록한다.

전체 승인→요청 시간은 다음 실제 신규 릴리스에서 측정한다. 위40초는 공통 Windows 검사 재현 시간이며 전체 전송/승인 처리 시간의 보장값이 아니다. 사용자 PC 적용은 서버 게시와 별도다.
